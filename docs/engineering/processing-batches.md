# 照片处理批次

第二阶段源码记录：工作台的照片列表、预览切换、JPG 导出以及失败重试现在限定到当前处理批次。原先 `photos` 是全部历史照片，不能直接用作用户所说的“这一批”。

## 用户入口

- 初次本地导入建立批次；“继续导入”追加到当前批次，“新建批次”建立空批次。工作台显示批次名称、已可用照片数量，并可以切换历史批次。
- 普通相机传入每个传输队列单独归组，处理批次 ID 与传输 batchId 相同。自动／选定发送接收按接收轮次归组，后续接收的照片追加到同一组。
- 相机前台传输启动后，工作台关注该批次；若本地导入、导出或创建批次正在执行，保留正在工作的批次，用户结束操作后可以手动选择新相机批次。只含视频的传输不产生可编辑照片。
- 切换／新建批次清空本次界面的导出结果和失败重试选择，不删除历史照片、传输记录或已导出的文件。此轮未加入批次删除、照片移动或复制功能。
- JPG 尺寸、质量和导出目录仍是工作台偏好，默认 100%／95／系统相册。后续源码已接入 Room 5 LUT 配方、Room 6 逐张胶片／首张继承及 Room 7 共享画框；这些是批次设置，切换批次各自恢复。

## 存储与提交

Room 4 新增 `processing_batches(id, title, createdAt)` 和 `processing_entries(photoId, batchId, ordinal)`。成员表仅对批次设置外键；photoId 是主键，保留单一归属，可以在照片尚未导入前登记。待导入的成员没有 PhotoRow，因此不会显示成空照片，也不会加入导出快照。

本地导入先生成照片 UUID、登记批次和顺序，再沿用该 UUID 写入 SourceManifest 与照片目录。若文件完成但 Room 提交前退出，恢复沿用预先登记的归属；没有归属的既有完成副本归入“历史与恢复照片”。相机普通队列的批次、任务及照片成员在同一事务登记；发送接收在追加照片任务的事务中登记成员。完成照片与队列 IMPORTED 状态仍在同一事务提交。

同批成员按登记序号排序，相机首次登记采用任务顺序。若用户在暂停的接收批次中追加了本地照片，之后新增接收成员取不小于当前尾部的序号，避免与本地成员冲突；恢复已登记成员不会再次追加或改变归属。

批次列表使用 Room 的事务嵌套关系读取；不把两个独立 Flow 的半更新列表拼接。界面再排除缺少私有 JPEG 的照片，仅提示缺失、保留数据库记录。DataStore 新增 `processing-batch-id`，与当前照片 ID 一起恢复；旧设置没有此字段时先找到旧当前照片所属批次，再选有照片的历史批次。

导出开始捕获当前批次照片、效果配方、共享画框、JPG 设置和目标；批次切换在操作期间禁用。通知触发的相机传输也不会在本地导出中途替换当前批次，已发布成功回调继续归于原来的导出。失败重试从当前批次中过滤失败照片，画框片号沿用该批次位置。

Room 7 的 `6 → 7` 只新增 `batch_frame_recipes`，每批一份版本化 JSON。旧批次缺少设置时使用无框；不覆盖 LUT／胶片配方，不操作照片或原始资源。配置及接口见 [画框功能](frame-export.md)、[前端交接](frontend-contract.md)。新迁移和绘制没有执行验证。

## 3 → 4 迁移

迁移只添加表和索引，不改写照片、原始文件、传输状态或已保存 URI。既有相机队列按 batchId 建组，任务 ID 成为预登记成员；照片 ID 与任务 ID 对应的原有照片自动出现在对应批次。其余原有照片保留原 ordinal，并统一归入“历史与恢复照片”。没有旧数据时不额外生成历史组。

来源是本应用现有数据结构，迁移不读取旧 Film Companion 的数据库。迁移语句与实体声明已作源码审阅，**尚未编译、执行迁移、运行测试或打包**；没有生成 Room schema JSON，不宣称数据迁移已经验证。大量历史批次读取、导入中断恢复、服务与界面交接及实际导出范围仍需在用户要求验证时确认。

实现依据：[Room 嵌套关系与事务](https://developer.android.com/training/data-storage/room/relationships/nested)、[数据库迁移](https://developer.android.com/training/data-storage/room/migrating-db-versions)、[外键](https://developer.android.com/reference/androidx/room/ForeignKey)。
