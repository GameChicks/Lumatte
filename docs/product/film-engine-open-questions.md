# 胶片引擎待解决问题

初始记录：2026-10-10。更新：2026-10-11 用户要求推进移动端性能优化，并由另一个前端负责 UI。此文件保留问题和真实证据边界，不代表已经完成测量。

## 已有反馈

用户自行在电脑部署 spektrafilm，认为模拟效果非常好，但全分辨率渲染在电脑上也较吃力，因此担心 Android 移植的性能。用户还反馈其夜景 halation 较弱，几乎看不到；希望既然提供开关，就能明确看到开启与关闭的区别。

## 已确认的产品约束

| 可见控件 | 用户期望 |
|---|---|
| halation | 能明确比较开／关差异，尤其是夜景光源；详细实现与强度映射后续确定 |
| 柔光 | 关闭、1/8 黑柔、1/4 黑柔、1/2 黑柔，档位有可见区别 |
| 统一曝光 | 最新要求将曝光补偿与相纸曝光合并，前端只显示一个曝光控件 |

胶卷选择保留原选卷流程。其余专业参数按胶卷内置或使用合适默认值，隐藏精细调节，不把 spektrafilm 的整套参数搬到用户界面。黑柔档位是产品中的效果等级；未经实体滤镜对照，不声称等同某品牌滤镜的实测物理响应。

## 后续研究任务

1. 定位全分辨率热点：光谱运算、可预计算数据、空间效果、内存峰值及数据搬运分别占多少；用户反馈不能代替 Android 证据。未获用户明确测试要求前不运行性能测试或基准。
2. 评估保留 spektrafilm 成像特征的预计算、缓存、低分辨率空间效果与 GPU／分块实现。不能以更快为由未经评估就将主要成像流程替换成普通 LUT。
3. 将此前提供的 SpektraLab、filmify、Phos、Phos_refactor 与 spektrafilm 比较：效果、移动端运算负担、可移植性和许可；现在不宣称哪一个更适合手机。
4. 核对夜景 halation 不明显的原因，包括阈值、曝光所在阶段、扩散半径、色彩空间和默认强度。区分 halation 的有色高亮扩散与柔光的广泛散射，避免两个开关只做同一种模糊。
5. 设计四档黑柔的可辨识映射与内部预设；保持原图细节及肤色。文档中的等级暂不换算为未经测量的透过率或半径。
6. 核对统一曝光的亮度与色彩响应。当前源码采用 −3～+3 EV 输入曝光、禁用相纸自动补偿、相纸内部倍率 1，不能把同一个 EV 叠加到两个阶段；逐张／首张继承、预览与导出共用配方。

## 原型阶段边界

### Halation 的源码定位（尚未做图像验证）

当前固定版本 `engine/src/core/params.cpp` 的 `apply_halation_preset` 按胶卷防光晕标签选择反射强度：strong 的 RGB 为 `.015/.005/0`，weak 为 `.08/.02/0`，no 为 `.30/.10/.015`。`halation_amount` 默认 1；仍然没有与用户夜景照片对照，不能只用参数大小断言视觉差异已经达标。

`engine/src/pipeline/pipeline.cpp` 的 `node_boost` 位于底片曝光链，先检查 `boost_ev`；默认 0 时直接跳过增强。其保护阈值是 `min(.184 × 2^protect_ev, max_raw)`，默认 `protect_ev=4`。如果这一阶段的最大值不高于该阈值，开启非零 boost 也会跳过；这里的 raw 是管线内部胶片曝光平面，不能直接当作 JPEG 的 0～1 sRGB 值或传感器 RAW。必须先确认实际阶段范围再调整阈值。

高亮 boost 是独立节点，Halation 的 `active=false` 仅跳过后续散射，不能自动关闭此前 boost。后续若为开关映射非零内部 boost，必须同时明确关闭时的参数，避免开关关闭后仍修改高亮。提高 boost 会改变核心高亮曝光，不只是光源周围的红色扩散；本轮未盲目开启增强或对所有胶卷移除防光晕层。夜景可见性仍是未完成项，黑柔计算优化不当作 Halation 的视觉修复。

### 接入边界

2026-10-11 用户要求优先推进传输之外的功能：现在进入影像编辑原型，传输遗留适配不再阻塞胶片模拟和 LUT 的开发。原型可先使用明确标注的固定内部参数，不向用户暴露尚未落地的空控件；性能、可见效果及成像一致性仍需在后续实际实现后解决，不凭文档宣称达标。

最新源码接入 C++／Vulkan 光谱管线、统一曝光、模型 Halation 和自有三档黑柔；增加 960 默认预览、大图分带、查表输入转换、串行处理与原生取消排空。详见 `../engineering/film-engine.md`。数值资源和目录元数据有来源记录；没有编译、渲染或测量，不宣称已达到手机可用速度。还需继续解决全图内存、GPU 兼容与后备路径、夜景光晕可见性。

随后加入光谱／LUT 效果预览 LRU，画框参数变化而处理尺寸不变时复用效果图，最多 2 张／8 MiB。原生 CPU 双 LUT 直接扫描位图，保留 Kotlin 后备及现有插值、强度和颗粒规则；应用退后台请求清理缓存。见 `../engineering/mobile-processing.md`。没有渲染、编译、数值对照或测量，不能把缓存命中或原生库成功加载当作速度达标证据。

继续减少黑柔高斯／整图插值的重复地址计算，并为后台清理排队释放胶片 GPU 引擎和空闲池。释放等待此前任务结束，不取消导出，下一次胶片请求重新初始化。仍没有实际耗时、内存峰值或效果一致性证据，不改变手机性能待办的完成状态。

最新用户明确允许比较其他算法，并把最终性能／效果平衡选型交给开发方。已完成固定源码结构研究，新移动主路线选择 spektrafilm 模型来源、密度域预计算、有界空间处理，主要参考 Filmify，不直接采用 Phos／Phos_refactor 替换胶卷色彩模型。新后端、数据包、GLES 分块和 CPU 后备尚未接入；现有 Vulkan 继续参考与当前执行，新增分段 staging／128 线程组源码不当作性能达标。详细依据见 [算法选型](../engineering/film-algorithm-selection.md)。

后续已生产 20 个独立三阶段数据包，并实现模型读取／4 MiB 缓存和 CPU 色彩核源码。v1 将曲线与局部 DIR 耦合一同烘入显影表，空间 DIR 暂省略；Halation、黑柔和密度颗粒仍待运行时接入，不能只用无空间的色彩核冒充完整手机胶片效果。当前默认 Vulkan 未切换，实际差异／误差／耗时仍未核对。见 [移动模型](../engineering/mobile-film-models.md)。

最新默认移动路径已接 GLES 分块和从原 JPEG 重做的 CPU 后备源码、有界空间场、黑柔／Halation 与近似密度颗粒，完整 Vulkan 独立保留参考。Halation 开关关闭不留高亮 boost，开启采用候选艺术强度下限；没有照片证据证明夜景开关差异达标，也没有三档黑柔对照。颗粒采用密度相关方差与相关噪声近似，省略精确粒子抽样和子层，不称与桌面相等。实际效果／性能仍需继续，见 [图像后端](../engineering/mobile-film-rendering.md)。

固定 spektrafilm 来源缺少黑白模型，因此新增两项独立、自有且明确标注的银盐风格数据，复用同一三阶段与批量接口；不是品牌胶卷实测标定，见 [黑白功能](../engineering/monochrome-film.md)。生产资源已经执行，Android 编译与实际照片处理仍未执行。
