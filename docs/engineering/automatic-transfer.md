# 待发送模式与自动传输

记录日期：2026-10-11。依据为用户提供的 Lumix Sync 2.0.15 APK 的只读 JADX 恢复资料；原始 APK 不修改，恢复源码不加入应用构建。以下是源码分析和实施记录，不是真机兼容结论。

## 两种待发送模式

握手成功不能只保留“已连接”。`accctrl` 的三个成功回复有不同含义：

| 回复 | 本项目枚举 | 初始化与目录 |
|---|---|---|
| `ok` | `BROWSING` | 普通回放初始化，从媒体目录浏览、多选传入 |
| `upload_bt` | `AUTO_UPLOAD` | 拍后自动发送；读取 `getinfo&type=allmenu` 中的指定目录，不调用 `playmode` |
| `transfer` | `MARKED_TRANSFER` | 相机选定文件发送；目录为 `dir_id_mark_list`，不调用 `playmode` |

`AUTO_UPLOAD` 的目录来自 `autouploaddirinfo/autouploaddirlist`。官方样本选择第一个父 `dir` 内最后一个子 `dir` 的 `object_id`。当前独立解析器保留这项选择规则；目录为空、为 `0` 或结构不可识别时明确失败，不改用相机根目录或猜测其他目录。专业参数菜单只作为获取目录的响应来源，不向用户开放其中的遥控能力。

`get_content_info&value=<object_id>` 用于读取待发送数量。XML 字段 `total_content_number` 的 `4294967295` 是忙碌哨兵，不是媒体总数。当前按忙碌响应有限重读，缺失、负数、超出 Int 范围及未经确认的 CSV 数量格式不作为有效数量。数量为零时不发 SOAP 浏览请求；非零则读取指定目录，复用已有的分页与 UpdateID 检查。

## 当前已经接入的源码

- 会话保留实际访问模式。普通浏览初始化仅允许 `BROWSING`；待发送模式走独立初始化。
- 工作台显示拍后自动发送／相机选定发送的区别、相机报告的数量和实际浏览列表，可以刷新、分页和断开。
- 待发送模式只允许浏览此次会话确认的指定目录。重连不把普通模式的旧目录和选中项搬入待发送模式。
- 用户点击“接收待发送文件”后创建或复用本相机的接收记录，由已有前台服务执行；每次只登记目录首项，保存后重新查询下一项，目录清空即结束本轮。
- 文件复用 `TransferRunner` 的 JPEG／RAW 内嵌 JPEG 导入与原视频发布、断点文件、稳定任务 ID。DIDL 父目录可以与发送目录不同，接收器按本会话指定的发送目录重新解析资源，不沿用旧地址。
- 相机选定发送在核对已保存结果和当前首项后尝试一次目录确认。拍后发送不发送该确认，改为检查目录是否前进。
- Room 分别保留接收轮次、当前文件和每个文件的确认状态。启动将进行中的确认改为 UNKNOWN，文件保存状态继续保留。
- 界面及前台通知显示保存数量、当前待发送数量；接收历史即使没有文件任务也可继续或停止。普通多选队列不能绕过接收器处理待发送模式。
- 活动接收旁路调用 `getstate&type=keep_alive`，每次成功后间隔一秒；忙碌状态有限重读，其他失败暂停接收。该请求使用同一相机 Network，会在下载期间运行，不等待流式 GET 的命令锁。

协议入口为 `LumixCameraSession.kt`；接收执行为 `IncomingTransferReceiver.kt` 和 `TransferRunner.kt`；持久记录为 `IncomingTransfer.kt` 和 `WorkspaceDatabase.kt`；UI 和服务入口为 `CameraController.kt`、`IncomingQueuePanel.kt`、`CameraTransferPanel.kt` 和 `CameraTransferService.kt`。

数据库版本升为 3，2 → 3 新增 `incoming_transfers` 表和 `transfers.cameraAcknowledgement` 可空列；原照片、普通任务、视频 URI 和设置不删除。接收轮次与首项任务同事务登记；文件确认状态与轮次的当前确认状态同事务提交。各版本尚未编译，未生成 schema JSON 或执行迁移。

| 确认状态 | 含义 |
|---|---|
| NONE | 此首项尚未提交保存结果 |
| READY | 照片目录或视频发布已提交，且结果可访问 |
| IN_FLIGHT | 发出目录确认前已持久化，正在核对或等待响应 |
| CONFIRMED | 已取得成功确认响应，并持久化到文件和轮次记录 |
| UNKNOWN | 请求或响应中断；没有可安全重发的证明 |
| ADVANCED | 不发送新的目录确认；拍后模式无需 transfer 确认，或原文件已不再是待发送首项。此状态不证明相机收到成功确认 |

## 后续接收与确认必须保留的区别

官方样本的相机选定发送分支，在文件复制成功后使用：

```text
mode=notify&type=transfer&value=ok&value2=<发送目录>
```

失败和取消分别有 `ng`、`cancel` 分支。请求只有目录参数，没有文件 ID。`getprogress&type=transfer` 是进度读取，不是成功确认。拍后 `upload_bt` 分支在复制成功后重新查询目录，样本中没有走相同的 `notify transfer ok` 分支；不能把两者合并成通用的成功确认。

接收器先完成照片目录／视频发布的持久化，再核对结果可访问性并进入相机确认。尚未落盘、仅收到部分字节、RAW JPEG 提取失败或已保存结果暂不可访问时不发送成功。暂停和停止保留已经落盘的结果。停止此接收只结束应用处理，不自动发送参考软件中的 `ng`／`cancel`，不替用户退出相机发送模式。

发送确认前登记 IN_FLIGHT。连接在确认发出后、响应落盘前中断，会出现确认结果未知的窗口。因为指令不包含文件 ID，当前资料不能证明重复确认幂等，也不能保证重发仍指向原文件。UNKNOWN 的文件仍为目录首项时暂停，不重发、不重复下载。用户继续核对时，原文件若已不再为首项，可以记录 ADVANCED 并处理新的首项；此结果不当作对应确认成功。每项历史确认保留在任务上，不随当前首项切换而覆盖。

目录更新滞后时先进行最多五次间隔 400 ms 的读取。已保存项持续位于首项则暂停；新的首项若匹配同一相机、发送模式及目录的历史保存元数据，也暂停并提示核对。匹配依据为媒体 ID、父目录、标题、原文件名、类型／容器和长度，不是内容哈希，可能遇到相机 ID 或名称复用，不能宣称绝无重复或误判。未支持的首项不会被跳过后向其他项发送确认。

尚需继续的内容：`getprogress` 语义及更多确认歧义处理、STA 的更多通知与机型差异、真实型号和目录顺序差异。普通连接固定为模式 3；SoftAP／STA 的相机发送通知触发模式 1／6 初始化和显式更新发送连接已接入独立入口，见 [蓝牙连接](bluetooth-connection.md)、同路由器连接。不提供通用模式字节接口。单轮接收清空目录后结束，后续接收由用户另行开启；没有实现后台自动重连或开机接收。

## 已连接发送模式中的后续拍摄接收

2026-10-11 接入源码。通过蓝牙读取资料并连接到对应 Wi-Fi Network 后，只在该 HTTP 会话确认为 `upload_bt`／`transfer` 且蓝牙实际具有两种发送通知时显示“接收当前及后续拍摄”。没有根据蓝牙广播名字推断其他已连接相机。进程内保留蓝牙地址、SSID、事件能力和选定 Network 的关联，不保存密码或系统 Network 到数据库。

用户启用后，已有前台服务重新打开所选 GATT，用本应用身份核对 SSID 并订阅两个发送通知；密码资料在订阅前释放引用。服务先接收当前目录；目录清空后将同一接收记录设为 WAITING，等待 BLE 事件。期间保留 Wi-Fi、GATT、保活和现有服务锁，不通过无限重复浏览发现新照片。接到事件后继续使用同一批次和首项任务规则，不另开竞争的接收器。

| 通知 | 所属服务 | 行为 |
|---|---|---|
| 图片事件 `48669da0-3217-11e6-b08d-0002a5d5c51b` | `6b005f20-3214-11e6-a5ac-0002a5d5c51b` | 首字节 1／2 触发读取待发送目录，3 停止本次观察并暂停未完成任务 |
| 模式事件 `e182ec43-3213-11e6-ab07-0002a5d5c51b` | `054ac620-3214-11e6-ac0d-0002a5d5c51b` | 1 为拍后模式、4 为选定发送；同当前 HTTP 模式时唤起接收，不同则暂停并生成新模式连接请求；2 表示结束；3 暂停并生成当前模式的网络资料更新请求 |

图片事件服务依据为 `C0393g.m1763T0(13)`；原参考说明把它标为主服务的描述在本次更正。模式通知依据为 `m1763T0(14)`。通知值依据为 `onCharacteristicChanged`，不是根据 UUID 名称猜测。

就绪事件使用合并信号，停止／断线／模式不匹配使用独立的结束信号，不能被新的就绪通知覆盖。结束信号也能中断尚在等待的 GATT 描述符回调。订阅后立即查询当前目录，以覆盖订阅前已经发生的拍摄；事件在保存过程中到来会保留一个后续触发，不并发执行相机确认。

普通 BLE 资料读取仍随操作或离开界面关闭；用户开启的后续接收归前台服务持有，不因 Activity 重建或切到后台而关闭。暂停、停止、BLE／Wi-Fi 断开、模式变化、保活失败或服务结束时释放本次 GATT，已保存结果和 UNKNOWN 规则保留。停止只结束应用处理，不猜测退出相机模式的值。进程终止后 WAITING 同 RUNNING 一起恢复为 PAUSED，不自动重新启用观察。普通“继续接收”恢复为单轮；再次观察需用户点击后续接收入口。

后续观察本身仅覆盖已经建立的发送模式和已关联的 BLE → Wi-Fi 连接，STA 发送关联也可启用。独立发送启动入口可等待相机通知后初始化 1／6；后续观察不发这些初始化写入，也不唤醒或自动重连相机。通知值 3 的资料重读和模式切换重新握手已由显式更新入口接入；保留原有 SoftAP／STA 路径，STA 更多通知、扩展服务事件仍需继续。当前最小工作台在后续接收期间仍按活跃传输占用工作台，等待时编辑／导出的并行协调留待影像引擎与正式 UI 接入。各项均未运行验证。

## 模式切换与资料更新

2026-10-11 接入源码。切换通知／已知发送模式中的资料更新通知会以带类型的连接更新异常终止当前 BLE 观察。先等待文件接收退出并保存 PAUSED／UNKNOWN，再关闭旧 HTTP 和本应用 Wi-Fi 请求；界面提供“更新发送连接”。已保存文件不撤销，旧批次不会改写成另一发送模式，不以连接更新重发相机确认。

更新请求由核心模块从已识别事件创建，包含目标模式及原因，只有进程内保存；相机 BLE 地址、原 HTTP 身份和 STA 用户输入的路由器名称也只由应用连接对象持有。用户点击更新后，重新用本应用身份读取当前 SSID／密码，允许相机网络名称变化，重新订阅发送与连接通知，再使用请求对应固定 1／6 初始化原网络路径。SoftAP 继续直连；STA 重新发送路由器名称、等待选择确认、写类型 2，发现绑定手机已有的一个 Wi-Fi Network。新会话先按原相机 UDN 和 HTTP 模式核对，再准备发送目录。UDN 缺失时只接受相同描述地址及型号；地址改变不能靠名称猜测身份，用户可用普通入口重新选择，旧队列仍按自身身份核对。

更新期间识别到另一模式，会把该事件作为新的更新请求，关闭本轮交接；失败／取消也保留入口以供用户重试，不无限自动重连。连接成功后由用户重新选择单轮或后续接收。同相机、模式及目录相同的未结束记录继续复用；另一模式的 PAUSED 记录保留，并可为新模式建立独立记录。Room 事务限制同一相机只有一条 RUNNING／WAITING，禁止竞争接收器。返回原模式时可继续其旧记录，UNKNOWN 规则依旧有效。

相机结束发送或图片停止事件会关闭本次连接，保留接收记录。启动恢复不重建进程内更新请求，仍需要用户重新连接。该流程是显式重新握手，不是无人操作的模式迁移；初次等待时若还不知道发送模式便收到资料更新通知，只提示重新读取，不猜测目标模式。
