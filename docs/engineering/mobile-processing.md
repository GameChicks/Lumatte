# 手机影像处理优化：源码接入

2026-10-11。本轮只改功能、应用生命周期和前端 API。没有执行 Gradle／CMake、着色器编译、渲染、测试、基准或 APK 打包；以下结构改进不能作为实际速度、颜色一致性或手机内存达标的证明。

## 原生 CPU 双 LUT

`native/lut/lut_jni.cpp` 是本项目既有 `CubeLut` / `LutRenderPlan` 的 C++ 适配，与光谱胶片库分开。它没有 Vulkan、光谱 profile 或服务器依赖，不把原生 LUT 可用性当作胶片 GPU 可用性。

JNI 直接锁住可写 ARGB_8888 软件位图，按 RGBA 字节和实际 stride 扫描；不创建整图 float 数组，不执行 Java 扫描条带的 getPixels/setPixels。两份 LUT 在任务开始复制为原生表，处理中只使用小 RGB 暂存；临时空间随表大小增长，最高规格双表约 7.8 MiB，不随照片面积增长。原图解码和最终画框仍需要整幅位图，此改动没有消除那部分内存。

保持原规则：1D shaper 线性插值，3D 红色索引最快的三线性插值，分别使用自身 DOMAIN／INPUT_RANGE；先槽 1 强度混合，再槽 2，之后单色颗粒、最终 8 位输出。第二槽读取第一槽的未量化结果；两次处理之间不先截成 8 位。颗粒仍由照片 ID 的 Java hash、有效源图坐标和原来的整数混合生成，uint32 运算保留 Kotlin Int 的环绕位模式。输入 alpha 不改写。CMake 禁止浮点乘加合并，不启用 fast-math；这些是保留语义的源码措施，未经对照不宣称两种实现逐像素相等。

原生 CPU 路径只在 `lfm_lut` 成功加载时使用；库缺失／不可加载时仍走原来的 Kotlin 32 行缓冲算法。正常原生运算失败不自动在半处理位图上再套一遍 LUT；返回错误，由调用方丢弃本次私有处理图。每次任务独立持有 LUT 副本，原始 `.cube`、私有解析缓存和导入 JPEG 不改写。

NativeLutRenderer 单线程执行任务，逐行检查取消。取消入口与任务释放共用锁；调用协程取消会等待原生退出后返回，调用方才能释放位图。输出发布继续沿用不可取消提交段，整批导出取消不会删除已发布照片。原生 library 加载失败、运算错误、内存不足、取消与真正性能证据是不同状态。

## 胶片和 LUT 效果预览缓存

`PhotoProcessor` 内部按源照片身份／路径／文件长度／时间、有效尺寸／方向、实际处理像素尺寸、完整配方、解析后的 LUT 对象和胶卷目录元数据建立效果缓存。解析表对象变更会失效，即使前端沿用同一个 LUT ID，也不会误拿旧表的图。导入源 JPEG 是应用不可变私有副本；自定义前端若主动替换同路径同长度同时间的文件，需要显式清空缓存，不利用这条接口改写用户原件。

效果缓存保存照片处理结果，画框、文字、签名、Palette 和片号仍在其后独立绘制。当边框设置变化但照片处理像素尺寸不变时，无需再跑光谱／LUT。比例或边框几何让照片在预览画布中的尺寸改变时，会重新计算相应尺寸的效果，避免用低分辨率预览冒充清晰结果。

缓存采用 LRU，最多 2 张、8 MiB，按 `allocationByteCount` 计费；超过预算的效果图不缓存，不因此降低预览或正式输出尺寸。缓存持有自己的不可变副本，返回前端的图都是独立可写副本，不把缓存的位图借给 Compose。释放／替换前端图不会破坏缓存，缓存淘汰也不会释放前端正在显示的图。额外缓存副本内存不足时跳过缓存；命中副本分配失败时清空缓存再走正常处理。临时处理图、前端持有的图及 GPU 内存不属于 8 MiB 预算，不能将这个数字当作应用总内存上限。

编辑预览和含框导出预览共用串行门。缓存读取、写入和清理都在该门内执行；不在当前处理／绘制时回收其输入。取消发生在 Default 调度器向前端交付结果的窗口时，会释放调用方未收到的位图。正式 JPEG 导出不读预览缓存，不将缓存的小图放大为成片，仍默认 100% 有效输入尺寸。

## Vulkan 上传与回读分段

`native/film/adapt_vulkan.cmake` 在未来获准构建时生成 Vulkan 后端副本，以本项目的 `film_vulkan_upload.inc`、`film_vulkan_read.inc` 替换两个传输方法；上游原件与原始清单不改写。应用构建使用这份副本，其他分配、计算着色器和数值模型保留。

原路径按完整传输长度申请并保留上传／回读 staging；大图会多出整幅 float32 输入或 RGBA16 输出大小的 CPU 可映射缓冲。新代码每次最多传输 4 MiB，分别复用上传和回读缓冲。每个方向的逻辑大小不超过 4 MiB，两个方向通常最多合计 8 MiB；这不包含驱动对齐、缓冲扩容时新旧分配短暂共存、原生输入数组、GPU 计算平面、最终结果或 Android 位图。不是应用总内存上限。

分段按连续字节偏移复制，不按照片空间拆分，不降低分辨率。double → float32 的表上传仍逐元素执行原来的转换，图像数据的精度、顺序和结果格式不变；没有运行数值对照，不宣称逐像素对应已经通过。4 MiB 边界及尾段保留四字节对齐；回读同时保留原有源偏移。

每段保留原有 host／transfer 屏障、非一致内存 flush／invalidate 和同步队列等待，GPU 完成后才复用缓冲。分段边界检查当前胶片任务的原子取消标记；JNI 将这种传输取消归为取消，输入、session 和结果仍由已有 RAII 排空释放。单次 GPU 操作没有被强制中断。依据：[Vulkan buffer copy](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdCopyBuffer.html)、[映射内存可见性](https://docs.vulkan.org/refpages/latest/refpages/source/vkInvalidateMappedMemoryRanges.html)。这两份 API 文档不是手机运行证据。

代价是大图传输分成更多同步提交，可能增加耗时；本轮只处理额外中转内存，不能声称更快。完整 GPU 平面、存储缓冲大小限制和 GPU／主机最终结果仍是后续工作。没有运行 CMake、编译、着色器或图像处理。

## Vulkan 线程组与限制

已固定的上游 shader／主机注册表使用 256 线程组；本项目生成副本改为统一 128，数学校准 shader 保留原来单线程。CMake 的同一常量生成主机头文件、逐 shader layout 和最大值归约 scratch，`Pipeline::device_max` 同步改为 256 个组 × 128 个线程，保持 256 个 float 局部最大值的缓冲大小。普通逐像素 shader 继续按全局坐标计算；颗粒种子不以组编号替代照片坐标。此改动尚未编译或数值验证，最大值归约的分组顺序变化也不能当作已证明一致。

Vulkan 核心只保证至少 128 个组内 invocation 和 X 方向 128 的组大小，256 不能作为所有设备的前提；依据：[Vulkan 限制表](https://docs.vulkan.org/spec/latest/chapters/limits.html#limits-minmax)。其他限制继续读取驱动，包括存储绑定数、存储缓冲范围与调度组数。它不证明所有 Android GPU 都能运行此管线。

Android 派生后端禁用上游仅针对桌面 CPU Vulkan 的超范围存储探测调用，不在引擎初始化时分配大型试验数组或突破驱动声明的 `maxStorageBufferRange`。原有小规模浮点校准保留以选择双精度补偿公式，未新增自动基准。Volk 原件已提供 `.so.1` 失败后加载 `libvulkan.so` 的分支，无需再复制加载器。新 shader 私有资源目录使用 `v2-mobile128`，不与旧目录混存或删除原图／配方。

## 生命周期与前端入口

`FilmMirrorApplication.processor` 是应用共享处理器，WorkspaceViewModel 复用它；新前端也应复用该实例，避免多套缓存和资源管理器。系统 UI 隐藏／后台回调请求清空预览缓存并释放闲置胶片引擎；旧 Android 的运行内存压力回调也接入同一路径。清理请求合并、异步等待串行门，不取消导出、不阻塞回调、不触碰前端持有的图。

胶片 GPU 的空闲缓冲池不属于位图 LRU；只清理 LRU 不能释放它。本轮增加 `clearProcessingCaches()`：先等预览门，再将原生引擎释放任务排入与胶片渲染相同的单线程队列，并取得同一个引擎互斥锁。此前渲染的结果／session 已释放后才销毁引擎、空闲 GPU 池及设置缓存。没有用过胶片处理时，不为了清理而加载胶片原生库。私有数值资源、源 JPEG、配方和已导出文件保留，后续胶片请求重新初始化引擎。后续队列任务仍可以重新建立 GPU 缓冲，这不是应用总内存上限，也没有消除当前渲染峰值。后台与取消时序尚未运行验证。

Android 14 起旧运行内存压力等级不再通知，不能依赖这些等级来守住内存；固定预算始终生效。UI 隐藏回调仍用于释放可丢弃的预览缓存。依据：[Android ComponentCallbacks2 官方文档](https://developer.android.com/reference/android/content/ComponentCallbacks2)。系统回调接入尚未以应用运行验证。

| PhotoProcessor API | 前端用途 |
|---|---|
| `lutBackend()` | 返回库加载状态对应的 `NATIVE_CPU`／`KOTLIN_CPU`，不做速度测试或初始化胶片 GPU |
| `previewCacheInfo()` | 返回实际保留字节数、数量、命中／未命中次数及预算；不是 FPS、耗时或应用总内存 |
| `clearPreviewCache()` | 挂起、等待当前预览安全结束后释放缓存，不改草稿／原件／成片 |
| `clearProcessingCaches()` | 另排队释放胶片引擎与闲置 GPU 池；下一次请求重建，不中途释放当前 session |
| `requestMemoryTrim()` | 合并式异步清理入口，供生命周期／内存回调调用 |

预览失败／导出失败仍通过异常和 `WorkspaceState.failures` 提供给前端。不要将 `NATIVE_CPU` 显示成“已测得更快”或“GPU 加速”。切换批次、曝光、LUT 强度及柔光后按完整配方请求预览，不手动复用上一张的像素。新的 LUT 导入后更新目录对象即可；重复读取整个目录会创建新表，安全失效但会损失缓存命中率。

## 尚需继续

黑柔继续保留现有线性 RGB／面积平均、三个高斯核和 `.125/.25/.5` 档位。本轮将高斯逐通道重复的地址／边界计算合并，整图回加用 O(宽＋高) 的一维坐标表，在三张散射平面和三个颜色通道之间复用采样位置；没有新增一张全分辨率空间平面。插值表达式、权重、每通道累加顺序与输出尺寸的源码语义保留；没有运行数值对照，不能宣称逐像素相等或给出速度提升。面积平均的长区域增加周期性取消检查。整体成像继续使用光谱管线，没有切换到普通 LUT。

胶片目前仍是完整光谱管线；没有用普通 LUT 替换。960 默认预览、分带、效果缓存、分段 staging、128 线程组和串行调用只能减少部分重复与中间开销。全图 GPU 缓冲、设备能力、手机内存峰值、CPU 后备、Halation 夜景可见性及黑白模型仍需继续。本文没有运行手机测试或作性能承诺。新增原生 LUT CMake 与 JNI 声明尚未编译，ABI、数值对应和实际取消仍待相应验证。

用户进一步授权自主选择手机性能／效果的平衡路线。新的工程选择为 spektrafilm 来源模型＋密度域预计算＋有界空间效果，参考 Filmify 的分阶段结构，优先原生 GLES 3 分块并保留相同模型 CPU 后备。当前新后端未实现，不立即改默认执行路径；选型证据与实施边界见 [算法选型](film-algorithm-selection.md)。
