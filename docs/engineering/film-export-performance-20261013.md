# 2400 万像素胶片导出优化

## 目标与证据

用户在 vivo X50 Pro+、Android 13、骁龙 865 上反馈：2400 万像素、Halation 开启、黑柔关闭，带画框的导出阶段约 35 秒。新目标为同等输入与效果下每张完整导出少于 15 秒。画框具体预设、JPEG 压缩质量、手机温度等尚未记录。

默认维持有效输入尺寸 100%；画框扩大后的画布仍按既有布局输出。不用缩图、关闭 Halation、移除画框或降低 JPEG 压缩质量来宣称达标。RAW 继续只提取内嵌 JPEG。

目前只有用户提供的旧版耗时，没有这轮修改在该手机上的运行结果。以下是源码优化及编译证据，**不是达到 15 秒的证明**。

## 已修改的路径

1. `lfm_mobile_film` 显式启用 `-O3`，Debug 原型也采用优化后的影像代码。修改前现有 arm64/x86_64 Debug 编译指令没有 `-O`；这说明编译设置存在性能隐患，不能据此推算它占了多少秒。保留 `-ffp-contract=off`，不开启 fast-math。
2. Halation 高光峰值分析、源图亮部提取、空间场的水平/垂直高斯滤波改为独立行分块并行；GPU 路线的 CPU 空间分析也受益。CPU 后备的全尺寸颜色与颗粒计算采用同样分块。每项最多四个工作线程，小图保留串行路径；不同时启动多张完整照片来增加内存压力。
3. 单元内累加顺序、阈值、核、三阶段表、效果参数和照片种子保留原规则。全体分析完成后才写像素，工作线程只访问各自输出行。取消或异常时等待所有线程退出，之后才解锁、回收位图。NDK 使用显式线程 join 保护，不依赖尚未提供的 `std::jthread`。
4. JPEG 解码要求可写的软件 ARGB_8888。正常方向且已达到所需尺寸时，直接转交这张私有位图，不再创建方向画布复制整图。2400 万 RGBA 像素对应约 96 MB（约 91.6 MiB）的临时位图；这不是应用总内存或实测峰值下降。旋转、镜像及需要缩放的照片仍走原方向处理。
5. 新增真实任务耗时记录，不自动跑基准：`writer.lastExportPerformance` 与日志标签 `LFMExport` 记录解码/方向、效果、画框、JPEG 编码、EXIF/同步、目标发布和总时长。日志带输入尺寸、压缩质量、尺寸比例、画框、Halation/黑柔状态；没有文件名、照片内容、相机地址或定位信息。此轮没有更改界面，前端可直接读取报告。
6. 报告记录本次实际采用的 GLES3/CPU 路线及当前进程最近的 GPU 失败原因，避免把配置的“优先 GPU”误认为实际 GPU 执行。GPU 失败仍先丢弃部分结果、重新解码，再从原图进行 CPU 后备；失败重做时间包含在效果阶段。

报告时钟从进入导出锁开始，到发布与清理结束；不包含锁前队列等待和页面动画。失败报告为 `completed=false`，总时长包含中断阶段，阶段列表只包含已经结束的阶段。日志只记录用户本来发起的任务，不增加图片处理、上传或计时循环。

## 编译范围

本轮 arm64-v8a、x86_64 的 `lfm_mobile_film` 原生库编译与链接通过；修改后的指令已包含 `-O3 -ffp-contract=off`。媒体模块及 app Kotlin 源码编译通过。所有工具与生成中间文件位于 D 盘。

没有执行单元、回归、冒烟、设备、图像、性能测试或基准，没有为本轮优化打包 APK/AAB。既有原型 APK 不包含这些尚未交付的修改。未证明取消运行结果、前后图像一致性、GPU 可用性、画框耗时或手机速度。

## 后续按实际瓶颈推进

在用户授权交付及手机核对后，用同一张 JPEG、同一胶卷与种子、同一画框/压缩质量对照完整导出。先看真实后端与阶段耗时，再决定是否需要 GPU 回读流水化、硬件浮点插值或散射网格细化；不把任何固定倍数当作已获得的加速。

若效果阶段仍超预算，再评估 Fotufilm 的逐尺度降采样高斯策略与更细的近场/更粗的宽尾分离。保留源像素亮部能量，避免先把小灯平均掉。原图输出分辨率不变。有关算法与新功能评估见 [Fotufilm 与后续功能](../product/color-film-feasibility-20261013.md)。
