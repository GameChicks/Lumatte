## 判断（推断，非证实）

- 权限不是原因：权限、系统定位、蓝牙均已就绪。BLE 连接和服务发现本身成功。
- 相机接受了手机标识写入，却拒绝了手机名称写入。与 `states=[0]`、`media-connect` 一起看，最符合的解释是：这台相机当时不在「蓝牙 → 配对」页面，而本应用生成的客户端 ID 从未在这台相机上登记过，相机在非配对状态下拒绝登记新手机。应用把状态 0 一律当作「已配对的重新连接」，没有这条路径的提示。
- 后三次连接超时更像是用旧扫描结果重试：相机在被拒绝后一段时间内不再可连接（或已退出蓝牙页面），而应用保留着旧列表，允许继续点同一个地址。
- 较弱的另一种可能是该平板与相机之间的蓝牙交互本身异常（陈旧系统绑定、GATT 缓存）。13.5 秒的服务发现和 NOTIFY 特征找不到描述符是这方面的旁证，但没有证据说明它们与 133 有因果关系。

没有看到这台 S5 在配对页面的广播内容，也不知道其配对页面广播的状态值，所以上述推断无法由日志证实。

## 本次修改

- `CameraBluetooth`：连接 GATT 前记录相机广播的状态（`advertised=pairing|normal`）和系统绑定状态（`bondState=none|bonding|bonded`）；记录 GATT 连接耗时 `gattConnect elapsedMs` 与服务发现耗时 `serviceDiscovery elapsedMs`；GATT 失败日志附带 `advertised=`。
- 手机标识/名称写入失败且相机广播的是「正常」状态时，错误提示补充：相机当时未处于配对状态，若这台手机尚未与相机配对，请先进入「蓝牙 → 配对」页面、重新查找并确认列表显示「相机正在等待配对」。措辞保留「若」，因为同一提示也会出现在首次配对后的第二轮连接里。
- `CameraController`：蓝牙在 Wi-Fi 交接之前失败（连接、读服务、登记、读取资料）时，清除旧的扫描列表和已选相机，并在错误提示末尾要求重新查找，避免用过期地址重试并白等 30 秒。用户取消和 Wi-Fi 阶段的失败不清除。
- 蓝牙列表里非配对状态的相机，说明文字由「相机已开机」改为同时提示首次连接需要先进入配对页面。

没有改动 GATT 读写顺序、身份编码、模式值、超时或 Wi-Fi/HTTP 流程。

## 下次日志里应看什么

- 扫描行出现 `states=[3]`、列表显示「相机正在等待配对」，流程行为 `phase=registration`。若仍只有 `states=[0]`，说明相机没有进入配对状态。
- `gattTarget advertised=… bondState=…`：`bondState=bonded` 而相机已删除配对信息，是陈旧绑定的线索。
- `serviceDiscovery elapsedMs`：确认 13.5 秒是否固定出现，以及是否与绑定状态相关。
- 若相机已进入配对状态（`advertised=pairing`）仍在写手机名称时返回 133，则需要重新审视该特征的写入格式或写入类型。
