# 胶片处理源码接入（2026-10-11）

状态：原生引擎、Android 调用层、批量配方与导出接口已写入源码。没有运行 CMake／Gradle，没有编译、解析或渲染测试，没有手机或性能证据，没有 APK。界面按用户最新决定交给另一个前端，本次不实现选卷页面或动效。

后续自主选型采用 spektrafilm 来源的分阶段移动路线，已实际生产另一版本链的 20 个响应／显影／扫描数据包，并写入懒加载读取器和 CPU 色彩阶段源码。生产资源生成不等于 Android 解析或照片渲染；完整 GLES／CPU 后端、空间效果及颗粒仍待接入，当前本文的 Vulkan 仍是默认执行路径。两套版本不混用，见 [移动模型数据层](mobile-film-models.md)。

## 来源与处理语义

- 采用 [SpektraLab](https://github.com/JamesQiu2005/SpektraLab) 的 C++／Vulkan 光谱管线，固定 `6a347d5756f8b1a96ec393c60bf5d0452fa5498b`。117 份选定源码、数值资源和许可正文保留在 `third_party/spektralab/upstream/`，字节及 SHA-256 记录在 `source-manifest.json`。未运行上游构建脚本或测试。
- spektrafilm 的效果是参考目标；原生移植不构成本项目与 Python 参考算法一致的实测证明。Python 参考版本记录为 `3bb2c2d2801ff68b92019cf1dbcbb133d60832bc`。
- 代码 GPLv3；原始胶片数据由 Andrea Volpato 提供，许可正文为 CC BY-SA 4.0。完整许可加入 `app/src/main/assets/licenses/`。本项目派生的显示目录沿用数据许可与作者署名。
- 目录元数据包含 20 个原始胶卷模型，类别来自实际 profile：负片、电影卷、反转片。黑白分类枚举保留，但目前没有接入黑白模型，不用彩色去饱和冒充黑白胶卷。
- 输入是相机或本地 JPEG，经方向处理后转换为线性 sRGB；RAW 仍只提取内嵌 JPEG。JPEG 不具有传感器 RAW 的动态范围，处理不能还原已经裁切的高光。
- 成像仍使用光谱曝光、密度、耦合、颗粒、相纸／扫描管线，不以普通 LUT 替换胶片模型。反转片使用 `scan_film=true`。

## 三个公开参数

2026-10-11 最新要求覆盖此前四个控件：只公开曝光 EV、Halation 开关、黑柔关闭／1/8／1/4／1/2。

曝光暂用 −3～+3 EV，传给曝光阶段；`product_defaults=true` 禁用相纸自动补偿，使单一曝光控件可以影响最终亮度。相纸内部曝光固定 1，不再应用第二份增益。这里的“合并”是一个可见参数与一致的响应，不把同一个 EV 同时乘进两个阶段。

Halation 调用模型原有的彩色散射。夜景可见性和默认强度尚未核对。黑柔是应用自有的线性 RGB 镜头散射：最大 512 长边的面积平均分析图，分离高亮后做三个半径的散射，再回加到原尺寸。三档映射 `.125/.25/.5` 是产品效果等级，未经实物对照不声称是某品牌滤镜标定。

## 第一批移动端优化

1. 数值计算接入 C++／Vulkan；原生引擎及其固定设置缓存跨照片保留，输入 sRGB 转换使用 256 项查表，避免逐像素重复幂运算。
2. `PhotoProcessor.preview` 默认长边 960，可在 64～2048 内请求，预览串行；这是预览尺寸，不改变默认 100% 的 JPEG 导出尺寸。
3. 超过 200 万像素的任务启用上游分带执行器。应用根据照片宽度、每像素 16 字节及暂定 12 份带内平面计算行数，48 MiB 分带预算，限制 32～512 行。上游 `strip_budget_bytes` 本身尚不决定行数，所以本项目明确设置 `strip_rows`。
4. 黑柔分析图固定上限；整批导出串行，释放本次 session、结果和输入 float 数组后再处理下一张。JNI 工作队列串行，避免两个大图同时占用原生引擎。
5. 批量草稿与原图比较分离；前端应合并连续滑杆请求、取消旧预览，调用方取消会等待原生退出后才允许回收位图。
6. PhotoProcessor 已加入最多 2 张／8 MiB 的效果预览缓存：同一照片、尺寸与配方复用光谱结果，画框和字体调整单独绘制。正式导出不使用小图缓存；后台请求安全清理。详见 [手机处理优化源码](mobile-processing.md)。
7. 黑柔高斯循环合并三个通道的地址计算，整图采样复用一维坐标表；保留原权重、档位及插值规则，没有实际速度／数值证据。后台清理增加排队释放胶片 GPU 引擎与空闲池，等待已有渲染结束后执行；下次请求重新初始化，不改变默认导出尺寸。
8. Vulkan 上传／回读用独立的 4 MiB 逻辑缓冲分段传输，避免这两处 staging 随整图增长；保留原精度、偏移、同步及非一致内存处理，加入分段取消检查。生成副本不改上游原件；完整 GPU 计算平面和最终图仍占整幅内存，更多同步提交的耗时代价未测量。见 [手机处理优化源码](mobile-processing.md)。

分带只减少可分带阶段的中间图；Halation、部分全图阶段、GPU 源图和最终结果仍占整幅图内存。不能据此承诺全分辨率照片已经能在普通手机稳定处理。当前还没有 CPU 后备路径、直接 GPU 输入或完整的大图空间分块。Vulkan 派生后端的线程组现统一 128，主机调度与最大值归约同步适配；仍需足够的存储缓冲绑定和范围，设备不支持时返回失败。Android 路径不采用桌面 CPU Vulkan 的超声明存储范围探测。

## 原始代码与本项目适配

上游原件不改写。未来原型构建时，CMake 在构建目录生成有明确锚点的适配：

- `pipeline.hpp` 的 RNG 初值来自每张照片的稳定种子；不会把首张颗粒位图复制到后续照片。
- `pipeline.cpp` 的节点取消检查增加本任务的原子标志。应用不跨线程写入上游会被渲染初始化重置的普通 bool，从而避开取消丢失和该字段的跨线程读写。
- `vulkan_gpu.cpp` 的上传和回读方法使用本项目分段实现，其他后端代码保持上游内容；构建目录副本引用项目内的两个 `.inc`，不覆写固定原件。
- 工作组注册表、计算 shader layout、归约 scratch 与主机归约调度共同采用同一个 128 常量；shader 和后端都生成副本，原件保留。原有数学校准单线程 layout 不改。

JNI 不在 GPU 节点中途释放资源，取消在节点边界或 CPU 行边界生效。单个 GPU 调用的取消延迟仍待实际验证。用户授权构建时才用 NDK 的 glslc 编译 34 个计算着色器并嵌入本地库，运行时写入应用私有资源目录；源码工作期间没有编译这些着色器。

Room 6 新增 `batch_edit_recipes` 表，声明 5 → 6 迁移，不清空现有照片／队列。各张草稿、首张稳定身份、模式及种子保存为配方，LUT 配方仍保留在原表。迁移尚未执行。

前端对接、进度与取消接口见 [功能交接](frontend-contract.md)。共享画框已接入功能源码，未实际渲染。性能、夜景 Halation、黑白模型和 GPU 后备仍需继续，见 [待解决问题](../product/film-engine-open-questions.md)。

用户授权自主决定性能／效果平衡后的后续主路线已选择密度域预计算和有界空间处理，参考 Filmify、保留 spektrafilm 模型来源；这属于新后端的实施决定，当前仍运行本文件所述的 Vulkan 源码路径。新后端尚未接入，不能把选型当作已经实现。见 [手机算法选型](film-algorithm-selection.md)。
